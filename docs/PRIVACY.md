# Allexi Bible data practices

This describes the implemented app. Before publication, the app operator must publish a privacy policy under its own name, add its support/contact details, and review the practices of its selected hosting providers. Set the resulting URLs as `EXPO_PUBLIC_PRIVACY_URL` and `EXPO_PUBLIC_SUPPORT_URL` for release builds.

Reading does not require an account. Login and editorial tools are restricted to approved administrators in the browser web app; the installed iOS/Android app has no login, signup or study sync. Published scripture updates remain public. Earlier native sessions may be retained in secure storage for compatibility; existing native annotations keep their local scope independently of token expiry. Study annotations and preferences are retained in the app’s local storage. Native authentication sessions are held in the operating system’s secure storage; browser sessions use origin-scoped browser storage. The app does not implement analytics, advertising, tracking, microphone access or location collection.

Administrator accounts are provisioned through Supabase Auth administration; there is no public signup form. Signing in on the web sends the email address and password to Supabase Auth. The application backend receives access tokens to authenticate requests, not passwords during ordinary sync. Account deletion requires the current password, which the API uses only to reauthenticate with Supabase; it is not logged or stored by the API.

When signed in, notes, bookmarks, highlights and reading position are synced through the Node API to Supabase PostgreSQL. Access policies restrict these records to their owner. API logs contain request identifiers, route paths, status codes and durations, not request bodies, email addresses, passwords or tokens. Hosting providers may additionally process network addresses and access logs according to their configured policies.

Web Settings includes permanent account deletion for administrators. It removes the Supabase Auth account, its synced study records and mutation receipts, and clears that account’s study data on the requesting device. Other offline devices may retain cached study data until it is removed locally; server access is denied after account deletion. Published editorial scripture and revision history are retained, with the deleted editor’s account link removed. Provider backup retention and any legally required records must be described by the operator before launch.

Recovery codes are sent by the configured Supabase email provider. The operator must configure a transactional email provider and publish a support channel for requests, including deletion requests from people who cannot sign in. A public web deletion-request route/form is also needed for the store listing if required by the selected distribution channel. Do not publish unimplemented contact methods or claim backup retention periods that have not been configured.
